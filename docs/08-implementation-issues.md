# 08. 実装ラベルの運用

> 本章は MVP の実装を GitHub Issue で管理する際の **ラベルの意味と運用方針** を定める。
> Issue の個別一覧・番号は流動的なため本章には載せない。最新の状況は [GitHub Issue](https://github.com/ryoohshima/AgendaTimer/issues) を直接参照すること。

## 概要

[07. ロードマップ](./07-roadmap.md) の **MVP（Android 初回リリース）** スコープを GitHub Issue 化し、親 Issue（Epic）と sub-issue で構造化している。設計（なぜ・何を）は 01〜07、進行管理（いつ・誰が）は GitHub Issue が担う。

- 各 Issue は単独でレビュー可能な最小 PR 単位（1 Issue = 1 PR）に分割し、PR の肥大化を避ける。
- 親子関係は GitHub の **sub-issue** 機能で表現。各 Epic を開くと Sub-issues セクションに完了率が表示される。
- ラベルでフィルタすると目的の Issue 群を抽出できる（例: `label:blocker`、`label:claude-code`）。

## ラベル凡例

各 Issue は **2 つの軸**でラベル付けし、「誰が・いつ着手すべきか」を判別できるようにしている。親 Issue（Epic）は `epic` で示す。

### 軸 1: 実装の主体（誰が）

| ラベル | 意味 |
|---|---|
| 🟢 `claude-code` | **Claude Code による実装が可能** |
| 🟠 `needs-human` | **人間による操作が必要**（アカウント・署名・審査・アセット等） |

### 軸 2: 依存位置（いつ）

| ラベル | 意味 |
|---|---|
| 🔴 `blocker` | **後続 Issue の前提となる土台**。先に倒さないと後続が詰まるため優先着手すべき |
| 🟢 `standalone` | **前後関係なく単独で実装できる**横断的/独立タスク。手が空いたときの並行作業に向く |

### 親 Issue

| ラベル | 意味 |
|---|---|
| 🟣 `epic` | ステップをまとめる親 Issue |

## 依存位置（軸 2）の判定基準

ラベルの貼り方を一貫させ、新たに追加する Issue にも同じ基準を適用する。

- **`blocker`** = 複数の後続 Issue の前提になる土台。先に倒さないと後続が詰まる。
- **`standalone`** = 他の機能実装の前後関係に縛られず、単独で着手・完結できる横断的/独立タスク。
- どちらにも当たらない中間ノード（単一の前提に連なるが後続を塞がない末端）は **ラベルなし**。

## 実装の進め方

- **`blocker` を優先的に倒す。** 後続が前提とする土台ゆえ、ここが詰まると並行作業が止まる。なお「全 UI の前提となる基盤」と「MVP 中核ロジック」は互いに独立しており、並行で着手できる。
- **`standalone` は依存チェーンの外**にあるため、待ち時間の並行作業に充てやすい。とりわけ Lint / CI 整備は早期に倒すと以降の全 PR の品質を底上げできる。
- **`needs-human` は実装後の配布フェーズ**など Claude Code で完結しない作業。実装完了を待ってから着手する。
- 進捗は各 Epic の Sub-issues セクション（完了率バー）で追跡する。
